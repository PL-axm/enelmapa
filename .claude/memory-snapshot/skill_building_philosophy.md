El usuario quiere ir armando un "stack" de varios skills para este proyecto
(menumap/EnElMapa) a medida que el trabajo real lo justifique.

**Regla acordada**: convertir un workflow en skill cuando se repite una
segunda vez con un caso real (ej. `cargar-menu-pdf` se creó recién después de
cargar dos menús distintos — The Burguery y Caficultor — no después del
primero). No crear skills especulativos para workflows que todavía no han
ocurrido dos veces.

**Why**: el usuario confirmó explícitamente esta secuencia ("si, agregalo y
haz un skill... ya que aca vamos a manejar varias cosas") después de que se
le propusiera esperar a un segundo caso real antes de crear el skill de carga
de menús, y luego pidió el mismo patrón para el skill de desarrollo
(`enelmapa-dev`) apenas se clonó el código — ahí el "segundo caso" es más
laxo porque pidió explícitamente "volverte experto" antes de que exista un
segundo cambio de código real; ese skill se creó desde la exploración inicial
del repo, no desde un patrón repetido — vale la pena confirmarlo si en el
futuro parece que se está creando un skill de más.

**Cómo aplicar**: antes de crear un skill nuevo sin que el usuario lo pida
explícitamente, evaluar si ya hay un patrón repetido real. Si no lo hay,
proponerlo en vez de crearlo directo.

**Además**: el usuario prefiere **definir procesos/flujos de trabajo de forma
colaborativa** ("definamos un flujo de trabajo") — para eso, proponer un
borrador y pedir ajustes antes de guardarlo como definitivo (memoria, skill o
doc), en vez de decidirlo unilateralmente y presentarlo como hecho.
